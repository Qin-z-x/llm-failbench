Quick-start demo

No install, no API key, no network. The kit is stdlib-only Python and the mock provider is deterministic: two demo runs produce identical per-probe statuses, counts and response hashes (run metadata such as run_id and timestamps differs).

  1. Validate the corpus and evidence (offline)

    shell 
    python -m failbench validate --strict

  2. Produce the deterministic demo run

    shell 
    python -m failbench run --provider mock --demo --out results/demo

  3. Regenerate this page and the Markdown report

    shell 
    python -m failbench report --results results/demo --out site

Runs from the repository root with plain python. The demo writes results/demo/results.json and results/demo/raw.jsonl so every attempt can be re-scored offline with python -m failbench replay --results results/demo --out results/replay (the --out keeps the committed demo artifacts untouched).

Why this kit exists

Benchmarks that depend on a judge model are hard to audit and hard to reproduce. FailBench is deliberately narrower: mechanical pass conditions, sourced claims, and a report that shows its own limitations.

Judge-free

Every probe is scored by one of a small set of mechanical rules: substring, regex, exact match, numeric tolerance, JSON-schema validation, or a conjunction of those. There is no LLM-as-judge, so a failure is a concrete mismatch between an expected and an observed string, not an opinion.

Deterministic

Prompts are static and self-contained; parameters default to temperature 0 and a fixed token budget; the mock provider is a pure function of the probe. Two mock demo runs produce identical per-probe statuses, counts and response hashes (run metadata such as run_id and timestamps differs). Capped raw responses can be replayed and re-scored without a network.

Evidence-backed

Each failure class in the atlas is anchored to publicly reported incidents from named sources (papers, issues, vendor documentation, discussions). Cards carry a source link and its popularity signal so readers can check the claim instead of taking the benchmark's word for it.

Methodology and threats to validity

Short version: each probe has exactly one mechanically checkable pass condition, every response is recorded, and nothing in the report is inferred by a model.

How a probe is scored

A probe declares a static prompt, decoding parameters, a repeat count, and a scoring rule from a closed set of mechanical types (substring contains, exact match, regex, numeric tolerance, a minimal JSON-schema subset, or a conjunction of these). Scoring normalizes whitespace and, where the rule says so, case. The scorer returns a boolean plus a concrete mismatch detail; those details are the reason fields on this page.

Run semantics

Statuses are pass, fail and error. Provider or runtime errors are recorded as errors and are never counted as model failures; they are excluded from the failure analysis and shown separately. Every attempt is written to raw.jsonl so a run can be re-scored offline with the replay provider. Repeat runs of the deterministic mock provider agree on per-probe statuses, counts and response hashes; only run metadata differs.

Severity weighting

weighted pass rate = Σ(weight × passed probes) / Σ(weight × attempted probes), with weights critical 4, high 3, medium 2, low 1. Provider errors count as not passed. The weighting is a presentation choice, not a claim of statistical importance: it is a fixed, published function so readers can recompute the summary from the per-class table.

What this page does not measure

It does not rank models, does not estimate production failure rates, and does not aggregate across runs. A pass rate of 64.0% on this corpus means exactly that many committed probes met their mechanical condition under the recorded configuration.

Threats to validity

  • Small sample per class. Per-class pass rates rest on a handful of probes; a single flip moves them by several points. Read the counts, not just the percentage.
  • Static, single-turn prompts. The kit measures controlled failure modes, not agentic or multi-turn behaviour in production, and it is not a general capability ranking.
  • Fixed, public probes. A model or prompt that has seen the corpus could overfit it. Treat scores as a regression signal for your own deployment, and add private probes for holdout.
  • Mechanical grading only. Pass conditions favour checkable properties (format, recall, constraint compliance). Open-ended quality dimensions are intentionally out of scope; a high pass rate is not evidence of general correctness.
  • Prompt and parameter sensitivity. Results are specific to the committed prompts, temperature and token budget. Changing any of them changes the measurement.
  • Version drift. Endpoints and models change silently; a run is a snapshot. Keep the raw transcripts (raw.jsonl) with the results to make runs auditable and replayable.
  • Evidence popularity is not severity. Atlas metrics (HN points, citations, stars) measure attention, not prevalence or impact. Classes under-reported in public discussion may be under-represented in the atlas.

Run it on your own endpoint

The kit speaks the OpenAI-compatible chat-completions protocol through the Python standard library. API keys are read from an environment variable and are never written to any artifact; raw prompts and responses are recorded without secrets.

Hosted OpenAI-compatible endpoint

shell 
# Any OpenAI-compatible /chat/completions endpoint works; keys are read from an env var
export FAILBENCH_BASE_URL="https://<your-host>/v1"
python -m failbench run --provider openai \
  --base-url "$FAILBENCH_BASE_URL" --api-key-env FAILBENCH_API_KEY \
  --model <model-name> --out results/run1

# Then generate the same kind of report for that run
python -m failbench report --results results/run1 --out site

Local server

shell 
# Local vLLM on the default port
python -m failbench run --provider openai --base-url http://localhost:8000/v1 \
  --api-key-env FAILBENCH_API_KEY --model <served-model-name> --out results/local

# Local Ollama on the default port
python -m failbench run --provider openai --base-url http://localhost:11434/v1 \
  --api-key-env FAILBENCH_API_KEY --model llama3.1 --out results/local

Set --concurrency to respect your provider's rate limits, and --class or --limit for a quick smoke run. Re-scoring is offline: python -m failbench replay --results results/run1 --out results/replay.

Use it as a CI regression gate

The gate compares a baseline result file with a candidate result file and exits non-zero when a probe that passed in the baseline now fails or errors, or when a baseline probe is missing from the candidate. It is a per-probe status comparison only: it does not compare aggregate scores, severity-weighted or otherwise. The demo provider keeps the gate testable offline; point the same command at a recorded live run to gate a deployment.

Compare two runs

shell 
# Baseline and candidate results, then a non-zero exit on regressions
python -m failbench gate \
  --baseline results/baseline/results.json \
  --current results/candidate/results.json

Adding probes

Add one JSON file to probes/<class>/<probe_id>.json with a static, self-contained prompt and a single mechanical pass condition. No harmful payloads, no private data, no long third-party text. A probe that cannot be graded by a fixed rule does not belong in this corpus. The schema and scoring types are documented in docs/CONTRACT.md.
